# 势途 GEO 工作台：积分定价与成本覆盖方案

调研日期：2026-09-14。状态：经营测算与待实施方案，未修改业务代码、线上套餐、模型配置或用户余额。

**建议采用“积分售价底线 + 功能/模型分档扣分 + 每任务成本上限”。仅调整充值送分，无法保证成本覆盖。** 新售积分含全部赠送后的实际售价不低于 0.20 元/积分；每积分承接的原始 API 成本预算不超过 0.05 元，另留 25% 费用波动准备金。按下文假设，推荐套餐贡献毛利约 59%–64%，再承担月固定支出、获客费用和历史积分履约成本。

这里的“保本”指在明确成本边界内，新售积分全部消费后仍能覆盖对应变动成本。它不等于无论销售规模、故障率、历史余额、人员费用如何变化，公司都不会亏损。

**三、实测记录说明的风险**

最近 7 天聚合快照：业务适配器事件 195 条，成功 177 条，其中 51 条成功事件缺少明确的 usage 记录，约占成功事件 28.8%。这里的事件可能是一个业务任务内的某一步，不是 195 个最终交付任务。千问/文心检测以及 Kimi 的部分路径，在当前代码中没有把全部 Token、工具费用写回成本台账。

同时记录了 1,635 条健康检查事件，仅 9 条成功。大量失败不代表厂商一定扣费；但这说明不能用全站“API 成功率”混合健康检查来推算客户任务成本，也不能把错误次数直接乘正常单价当成账单。

文章实际路径包括草稿、结构校验、语义裁判、必要的修复及再次裁判；批量任务还可能有类型分配。最近 7 天豆包 Pro 的小样本：3 条成功草稿事件累计输入 17,822、输出 21,402 Token；2 条修复累计输入 5,862、输出 15,058；3 条千问裁判累计输入 16,255、输出 1,532。按现价合计约 **1.251972 元**，除以 3 条草稿约 **0.417324 元**。

这只是同一时间窗内若干阶段合计除以草稿次数，不是逐任务关联后的单篇结算均价，不含无法取得用量的失败、类型分配及其他费用，也不是 P95。3 条草稿中，思考 Token 占输出约 83.2%；2 条修复中约 91.8%。文章字数无法代表计费输出量。

另有 10 条失败的 DeepSeek Pro 草稿/修复事件仍返回了明确 Token 用量；“业务失败退款”不能消除已发生的上游成本。必须把失败烧费计入成功交付的单位成本或独立故障预算。

三个可复算的风险场景：

1. **Kimi 检测单元：**假设各轮累计输入 10,000、输出 2,000 Token，执行 2 次百度搜索，裁判分摊假设 0.004 元，原始成本为 `0.065 + 0.054 + 0.072 + 0.004 = 0.195 元`。当前最大套餐每检测单元仅收 0.104743 元，单元差额约 **-0.090257 元**，尚未扣经营支出。这是代码允许出现的压力场景，不是已对账的 Kimi 实际均价。
2. **同套餐被集中消费：**若 35,000 积分全按当前 1 积分规则用于上面的 Kimi 场景，API 成本 6,825 元，收款 3,666 元，差额 **-3,159 元**。无需所有用户都如此；存在可持续的低价高成本使用路径就有风险。
3. **长文一次修复：**假设草稿与修复各输入 12,000、输出 12,000 Token，使用豆包 Pro；裁判合计另预留 0.03 元。原始成本 `0.864 + 0.03 = 0.894 元`。当前 8 积分最大套餐收入约 0.838 元，已经不足。再有账号切换、付费超时，成本更高。

过去的便宜模型调用仍可能有很高毛利，不能因此认定所有功能亏损；也不能用便宜功能的平均成本掩盖贵模型被集中使用的风险。

另一种更简单的备选是统一“1 元 5 积分”，取消金额越大积分越便宜，只用团队权限与服务权益区分档位。推荐表保留了现有套餐经营方式，迁移较平滑；选择统一比例也必须同步修复高成本功能扣分。

“基础模型”是用户明确选择且质量评测合格的方案，不建议暗中把当前豆包 Pro 降成 Lite。严格检测继续保留独立问题、所选模型、公开来源证据。豆包 Responses 搜索费用未核定前，其基础 2 积分档只能视为预算候选，不能据此承诺已完成保本验证。

例如选择豆包 Lite、千问、HY3、文心 4.5 Turbo、DeepSeek Pro、Kimi 六个平台，每问题为 `2+2+2+4+8+8=26` 积分；10 个问题总计 260 积分，按最大套餐约 52.95 元。报价页必须显示模型、问题数、复测轮数、预计扣分。重复检测按新任务计费，不能承诺无限复测。部分单元失败时，应退该单元原先预留的不同积分，不能继续按成功单元数乘统一 1 积分结算。

难度测评五阶段、长文修复和多轮工具的真实分布尚未完整对账，因此“20/50 起”等属于有成本上限的保守报价底价，不是从足够生产样本统计得到的均价。批量折扣仅在已验证的缓存/Batch 节省或人工节省确实存在时考虑。

**六、把“不会越用越亏”写成可执行的规则**

1. **完整计量。**每笔用户任务关联所有模型阶段、重试、搜索、修复与最终扣分。按渠道、模型版本、计费时段、输入档位记录原始用量、供应商请求号及费率版本。reasoning 通常属于输出、缓存命中属于输入子集，不能重复相加。补齐 Kimi/DeepSeek 工具循环、千问原生搜索、百度搜索生成、HY3 Responses 的记录，再与厂商日账单核对差额。未知费用独立列示。
2. **先报价再执行。**一次报价锁定模型、输入范围、阶段数、输出总量、工具次数、重试总预算及所需积分；长资料或高价模型重新报价。未绑定价格的自定义模型不进入普通积分收费路径。
3. **预算看整个任务。**目前单次 `max_tokens` 和超时不是整个任务金额上限；多阶段、账号切换、工具往返都会叠加。发出每个付费请求前，预留它最坏可计费的输入、输出及工具费用；正在执行的请求也占用预算。仅在事后看 usage 超额或触发 abort，挡不住厂商已执行的费用。无法约束工具次数的原生服务要按可核验的最大费用报价或暂不开放固定价。
4. **失败费用归属明确。**用户未拿到约定结果可以退款，但已付给模型的费用计入故障损失池。25% 准备金只是预算，不是无限赔付能力；账号欠费、连续超时、无有效输出时暂停该通道，保留可恢复结果，避免持续重放付费流程。退款与扣分继续使用现有原子和幂等机制。
5. **设置金额边界。**账号池当前所有 `daily_budget_cents` 都为空。现有预算估算器把输入输出合并、默认按 10 元/百万 Token 估价，不区分输出更贵的 Pro 模型及搜索费，不能直接当财务熔断器。需要按真实费率预留，并设置平台/租户/任务的可承受预算；具体日限额由可用现金和订单规模决定，不凭空指定。
6. **管理持续监测。**自动检测仍按每轮实际任务扣分，排队前检查积分与成本预算；并发只是速度限制，不能替代金额限制。探活和管理员测试单独列成本，避免混入客户单次服务成本。

保本公式：

`单次完整原始 API 成本 C = Σ[(未缓存输入×输入价 + 缓存输入×缓存价 + 计费输出×输出价)/1,000,000] + Σ工具费 + 其他按次供应商费用`

`完整交付的观测单位成本 = 归属于同类任务的全部实际费用（含失败）/该类成功交付数`

`任务最低积分 = ceil[1.25×C预算 / (积分售价底线×(1−支付费率−其他变动费率−目标贡献毛利率))]`

以 0.20 元、0.6%、10%、55% 代入，分母对应每积分可承受原始 API 成本约 0.05504 元。方案使用更保守的 0.05 元/积分。因此，在这些假设下每积分最低贡献约 0.1163 元，贡献毛利 58.15%。产品报价还可以高于该底线，但不能低于它。

`新套餐最多发放积分 = floor[实收×(1−支付费率−其他变动费率−目标贡献毛利率)/(每积分原始成本预算×1.25)]`

例如 3,666 元、目标 55% 时，公式最多约 20,177 积分；推荐 18,000 积分为成本变化留空间。已有实际费用完整计入 C 时，不要再把同一重试费用重复加一遍；额外 25% 用于测算误差及未来波动。

**七、ROI、固定成本和现金流**

“贡献毛利率”与“ROI”分母不同，不能混为一谈。

以 3,666 元/18,000 积分全部用完、达到原始成本预算上限计算：

- API 原始预算 900 元；25% 准备金 225 元；合计 1,125 元。
- 支付费假设 21.996 元；经营预留 366.60 元。
- 贡献余额 2,152.404 元；贡献毛利率 **58.71%**。
- 贡献口径投入回报率 `2,152.404 / (1,125+21.996+366.60)` ≈ **142.2%**。
- 上述准备金是保守预算，不等于全部已发生费用；尚未扣月固定成本、独立获客费用及历史积分履约缺口，不是会计净利润或公司投资 ROI。

若所有售出积分均按最大包有效单价消费，且每积分原始 API 成本维持 0.05 元：

| 每月固定支出假设 | 需实现的月度服务收入/匹配消耗额约 |
|---:|---:|
| 500 元 | 852 元 |
| 1,500 元 | 2,555 元 |
| 3,000 元 | 5,110 元 |
| 10,000 元 | 17,033 元 |

测算公式：`月经营余额 = 本月服务对应收入×贡献毛利率 − 固定支出 − 独立获客费用 − 历史积分履约缺口`。将充值现金流直接当收入、把尚未消费积分对应的未来成本忽略，会高估利润。这里是管理测算口径，实际收入和税费确认应按企业的账务口径替换。

同样按最大套餐价、不调整扣分的压力测试：原始 API 单积分成本为 0.025/0.05/0.075/0.10/0.15 元时，贡献毛利约为 74.06%/58.71%/43.37%/28.03%/-2.66%。即成本翻倍仍有变动成本空间，但固定成本未必能覆盖；接近三倍会重新出现单位亏损。达到 55% 目标时，每积分原始 API 成本最多约 0.05605 元；下降到纯变动成本保本时约 0.14566 元。这两个阈值用途不同，应提前按目标毛利调价，不要等亏损才停。

资金管理建议：每笔充值至少留出匹配未消费积分的原始 API 预算及波动准备金，按实际消费逐步释放；厂商算力充值余额是预付资产，不能把“本月充给厂商的现金”全部当作本月已消耗 API 成本。对公人工服务应单独计服务成本，不能用积分包附赠无限人工交付。会员累计充值权益若产生长期固定服务负担，要计入固定成本或另收服务费。

**八、免费额度与旧积分处理**

新用户当前默认获赠 50 个通用积分；子账号代码已有不重复赠送的处理，但主账号拉新仍有 API 成本。推荐新注册先提供样例体验，不默认赠送 50 通用积分。若保留 10 个限定基础模型的体验积分，按本方案成本上限及准备金为 0.625 元/注册；1,000 个体验用户约 625 元，2% 付费转化时仅体验成本就约 31.25 元/付费客户。该假设只用于获客测算，不代表真实转化率。体验积分不可抵付费余额或叠加造成售价跌破底线，历史已承诺权益另行处理。

历史 1,999 元/50,000 积分按原来 8 积分文章计算，摊到每篇收入只有 0.31984 元，低于上述 Pro 小样本阶段成本 0.417324 元。因此旧积分必须单列，不能以新套餐利润掩盖历史履约风险。

先按购买来源、已消费和剩余量核对旧积分负担；当前生产订单记录不足以推出剩余余额或确切损失。默认尊重已售权益，不直接清零、缩水、擅自改旧扣分或取消已支付订单。新规则只约束新售积分；如提出迁移，需把可继续使用的功能、价值和差额讲清并由用户接受。旧余额与新余额混用时要保留来源和对应规则。

历史低价积分的已承诺成本风险无法靠未来改套餐“保证消失”。可选处理是继续按原约履行并设置真实现金准备金，或协商迁移；不能把老用户剩余积分静默套新收费倍率当作保本措施。未支付的旧报价也要按其有效期与已有承诺处理，支付回调必须使用订单锁定积分，不能用新套餐反算。

**九、实施次序与完成条件**

1. 补齐按请求计量和搜索收费，核对厂商账单、实际折扣、支付费率、月固定支出；旧 `deepseek-chat` 等仍被使用的名称逐一核对供应商返回的实际模型，不自行假定等同新模型。
2. 将本方案套餐和功能报价放入独立版本，先回放历史 Token/工具记录计算模拟账单，核查普通与高消耗用户各自的成本覆盖；无需额外大量付费生成样本。
3. 接入任务报价、总成本预留、不同模型退款与预算阻断；重点检查重复回调、超时但上游计费、多轮搜索、部分成功、批量取消和任意自定义订单的价格底线。
4. 确认旧积分处理后再对新订单切换；新业务累计形成足够的完整样本后，用按模块/模型区分的均值及 P95/P99 复核报价，并以同周期厂商账单校准，避免把本轮 3 条草稿小样本当成稳定规律。

完成条件：每个公开售卖组合均有成本边界、利润测算与正确退费；未计价模型不能绕过边界；同周期厂商账单差异能解释；新充值全额消费时满足目标贡献毛利；固定成本和旧积分缺口已另列预算。

本方案的实际折扣、固定支出、正式支付费率及部分工具账单尚未取得，因此推荐金额是可实施的保守设计基准，不是已对全站完成的实际净利润审计。
