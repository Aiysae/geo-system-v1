# 文章 AI 调用排查与优化方案

日期：2026-09-22。代码基线：133e472c。用户确认症状：直接显示“生成失败／超时”。本轮未修改业务代码，未调用付费模型。

## 结论与证据范围

系统确有可复现的执行缺陷，以及会增加长文耗时、返工和重复计算的设计问题。优先修复完整响应的超时／取消处理，其次调整阶段预算、保存中间正文，再处理 Prompt 与质检一致性。暂不建议重写整个系统，也不建议简单换模型或一律延长超时。

这不是对最近线上失败原因的最终归因：当前未取得生产部署版本、近期失败任务的阶段日志和厂商账单。本地 .env.local 未配置 DATABASE_URL；只读连接其中配置的 Redis，扫描 geo:* 返回 0 个键，不代表生产环境没有任务。既有 9 月 7 日排查文档仅作为历史证据，不能替代今天的统计。

应区分：正文请求失败、文章已生成但质检待复核、任务存储／结算失败。用户此次报告的是第一类或第三类；当前新写文章的裁判异常通常被捕获并返回正文，不宜将裁判失败直接等同于用户所说的超时报错。改写分支另有修复异常、映射验证不通过直接失败的路径。

## 当前调用链

```text
单篇 / 批量 / 自动成文 / Agent
  → articleGeneration 后台任务（输入和任务标识保存）
  → background-jobs 直接调用文章 POST 处理器
  → 参数与资料前置检查、模型解析、积分预留
  → 编译方法、文章形态、标题策略、品牌结构、知识资产
  → 组装任务档案，普通新写文章检索公开网页
  → 长文规则生成写作计划（AI 规划默认关闭）
  → 正文模型生成
  → 本地规则检查
      ├─ 通过 → 长文语义裁判
      │           ├─ 通过 → 交付
      │           ├─ 明确不通过 → 整篇修复 → 本地检查 → 再裁判
      │           └─ 裁判异常 → 保留正文待复核
      └─ 不通过 → 整篇修复 → 本地检查 → 通过后才裁判
  → 最终正文、审计信息、归档和结算
  → 批量另做相似度检查，启用时可能再生成一次
```

来源：src/app/api/article-generation/route.ts:444、692、790、807、849、855、968；src/lib/background-jobs.ts:539、683；src/lib/article-batches/manager.ts:380。

长文常规是 2 次模型调用：正文 + 裁判。本地不合格后修复且规则通过是 3 次；初稿规则通过但语义不合格、修复后规则通过是 4 次。开启 AI 规划再加 1 次。批量相似度重做会再次执行这条链；以上不是 HTTP 请求上限，不包含账号切换、传输重试、策略分配。

普通短视频不走长文语义裁判；品牌单问题视频默认按配置决定是否补充公网资料。改写先独立分析品牌，再做一对一映射改写，必要时修复并重新验证，不走长文语义裁判。

上游策略任务由 article-strategy-service 使用辅助模型分配创作类型，不是每次正文必经的一轮。疑问句、调研、渗透检测等另有 adapter/pool 调用路径；不应把这些模块账单合并为“单篇文章成本”。文章专用 runtime、通用 ai-credential-chat、adapter 共享部分账号和底层兼容请求代码，但并非每篇文章顺序经过三套调用器。

## Prompt 实际植入方式

正文 system 由以下内容直接拼接：通用身份与事实边界 → 长文编译器规范 → 创作类型专用长模板 → 方法论编译出的结构、表格、平台、标题和质量要求。专用模板保留 {{核心疑问句}} 等说明性占位符，由模型结合 user 数据理解，未统一预先做字符串替换。

正文 user：成稿要求 → 规则计划 JSON → 客户主体、问题、优势、补充要求、批量差异 → 对比主体资料 → 方法参数和选定知识资产 → 搜索标题／摘要／链接 → 时间信息。

知识资产经 compiler 选取并通过 methodology.userAddendum 注入，不能因 buildArticleTaskDossier 没有直接读取 knowledgeBase 就断言资料丢失。对比主体在档案和方法参数中重复出现；任务、证据、计划在裁判和修复阶段又重复发送。

本轮测得，仅 getArticlePromptTemplate 的模板字符数（未加方法论、资料和正文）：第三方观察 6420、排名报告 5116、选型避坑 4738、实测横评 4908；这些都是字符数，不是 Token 数。长文输出上限统一为 12000 Token，上限不是实际每次消耗。

裁判收到独立审核 system，加任务档案、计划、全文和形态规则；修复收到校对 system，加问题列表、任务档案、计划和全文。它们没有原样复用正文完整的专用 system。9 月 7 日已补齐形态规则，但生成与审核仍有事实措辞冲突。

来源：src/lib/article-prompts.ts:25、47、119；src/app/api/article-generation/route.ts:184、310、580；src/lib/geo-methodology/compiler.ts:286、314；src/lib/article-content-pipeline.ts:133、275、329、391。

## 优先修复的执行问题

### P0：超时与取消保护只覆盖收到响应头之前，未覆盖正文读取

postChatCompletionWithTimeout 在 fetch 返回 Response 后立即清除定时器并移除父级 abort 监听；openaiCompatRaw 随后才 res.text() 读取正文。HTTP 响应头先到、正文延迟到达时，等待正文的过程脱离了这两层保护。

本轮本机真实 HTTP 复现：服务端先发送 200 响应头，300ms 后发送 JSON 正文；客户端设置 70ms 请求超时，100ms 父级取消。实际 324ms 后仍成功返回，parentAborted=true。

文章阶段计时器仍可设置超时标记，但其取消信号此时未传递到响应体读取。它可能只能在正文最终读完后报告阶段超时，不能保证及时终止在途读取、释放并发和停止本系统后续等待。厂商已经执行的计算也不能由本地取消保证退款。

位置：src/lib/llm/openai-compat.ts:141–183、415；src/lib/article-model-runtime.ts:473–515。

方案：保持同一请求的计时器和父级取消连接直到响应体读完；所有成功、错误及参数兼容重试分支统一执行清理。补“头先到／体慢”“头后取消”“读体阶段超过总预算”回归，不只测迟迟不返回响应头。

### P0：配置超时、单次超时和阶段超时不一致，错误提示误导操作

正文阶段总预算 300 秒，单次请求上限 180 秒，还要取后台模型 timeout 的较小值；账号排队也占用阶段预算。普通供应商账号最多尝试 3 个，每轮可排队至多 60 秒，受阶段剩余时间约束。

例如第一次请求耗尽 180 秒，第二账号最多只剩约 120 秒，排队还会进一步减少。并不是“3 个账号各有完整生成时间”。后台默认 article timeout 为 600 秒，但正文传入的 180 秒上限会覆盖它；错误提示却建议去后台增加模型超时。超过该上限后继续调大配置并无对应效果。

位置：route.ts:118、709、1047；article-model-runtime.ts:169、292；ai-settings.ts:65。

方案：先恢复可靠计时，再分开记录排队与模型耗时。以实际 P50/P95 和正文长度／思考模式确定预算；在剩余时间不足以完成一轮生成时结束切换。错误返回具体阶段、原因和已用时间，取消“统一建议增加后台超时”。

### P0：最终响应前没有持久化正文阶段结果

后台已有完整 job.result 时可以直接恢复保存和结算，这是有效保护。但 job.result 在整个文章处理器完成之后才保存。初稿、修复稿和裁判结果都留在该次处理器内存中；在审核期间进程重启、任务总超时或取消，已有正文仍可能不能交付。

位置：background-jobs.ts:683–695；route.ts:719–968。

方案：复用现有任务存储，只增加必要的“初稿已保存／修复稿已保存／审核状态”记录。重试同一任务时继续未完成阶段，保留不同任务独立生成的语义。先实现持久化初稿，不扩成通用工作流平台。

### P1：多层重试与错误归类仍可造成无效请求

正文兼容接口针对指定 429/5xx 默认再试一次；账号池最多 3 个账号；自定义网关另有同模型线路切换。阶段预算是时间约束，不是请求数约束。400/404 等也被通用 shouldFailOverAiCredential 视为可切换，输入或参数本身错误时换账号通常不能修复根因。

位置：article-model-runtime.ts:200、292、401；llm/openai-compat.ts:330；ai-credential-errors.ts:6。

方案：明确区分输入／参数错误、账户欠费／权限、限流、网络失败和内容验收失败。仅对可能成功的错误重试；对已执行但响应丢失的请求优先追踪厂商 request ID，避免盲目重复。保留现有同型号容错，不把所有 400 一刀切，因为部分供应商会以 400 返回账户问题。

### P1：截断的非空正文未单独识别

openaiCompatChat 对空内容检查 finish_reason；对非空内容未针对 length 单独标记。达到输出上限的半篇正文可能继续进入规则、裁判和整篇修复。

方案：将 finish_reason、request ID 和有效输出长度传给文章阶段；明确识别不完整结果，避免把截断当成普通文风质量问题。如何续写应保持事实与文章结构一致，不默认再从头生成。

## 增加返工和算力的 Prompt／质检问题

1. **确有指令冲突。** geo-article-prompts.ts:169 等要求缺少证据时写“暂未检索到可核验公开证据”；article-content-pipeline.ts 的裁判规则要求没有实际检索记录不能声称“未检索到”。同一文章可能因遵守写作模板而被裁判阻断。改为准确区分“输入资料未提供”和“本次检索未找到”，并由同一事实规则供两端使用。
2. **检索存在就要求引用。** 搜索主要提供标题和摘要，不读取核验每个目标网页；虽然有相关性过滤，仍不足以保证支撑文章事实。正文与本地检查要求至少使用一个检索结果，可能诱发牵强引用、随后被语义裁判否决。应先挑出真正可用的证据，只对已确认相关且有支撑关系的资料要求引用。
3. **字面重合被当作语义硬门槛。** article-quality.ts:80–105、412–425 使用双字／英文词重合并固定要求至少 2 个。已复现：核心主题为 GEO，正文明确回答 GEO，仍得到 question_drift、opening_does_not_answer；换成 GEO怎么做？这两项消失。单个有效词的输入永远达不到固定阈值。应按可用词数量设置合理下界，并把弱词面信号作为提示，交给语义判断最终认定。
4. **小问题也触发完整重写。** 标题层级、开头、表格、引用等本地失败会调用正文型号再输出全文，随后可能再次付费审核。对纯格式可确定修复的问题先本地处理；涉及事实和论证时保留模型修复。原稿和修复稿均保存，避免替换成更差或不完整版本。
5. **所有长文都同步裁判。** 正常 2 次、返工最多常规 4 次，且重复传入长资料。可把正文交付与审核状态分离，裁判继续保留；先解决状态与恢复，不用“取消审核”制造虚假的成功率。
6. **搜索放大请求量。** 默认至多 3 个外层查询，每次 webSearch 最多 4 个变体并行查 4 个搜索引擎，理论最多 48 个搜索 HTTP 请求。它不是 48 次模型推理，但会增加联网耗时和资源占用。按证据需求检索，资料够用后停止；同批公共资料可复用，独立文章仍正常生成。
7. **相似度重生成是条件成本。** 批量界面默认开启，达到阈值后免费再生成一次，“免费”只是用户积分层面，供应商调用仍发生。9 月 7 日历史文档称其当时 624 条记录未发现自动重写标记；今天没有对应统计，不能将它列为已证实的主要费用来源。

## 模型因素与历史变化

8 月 5 日 0c5336b0 增加写前计划、语义裁判和修复流水线。之前同一长文路径主要是正文 + 本地检查，必要时修复；成功定义和调用数量都发生变化。因此“以前顺、后来更慢更贵”有对应的代码演变，不宜只归因于模型退化。

9 月 7 日已实施：AI 规划默认关闭；裁判改为独立辅助模型，默认 qwen-plus 非思考；本地不合格先修复再裁判；裁判规则与形态对齐；稳定时间注入位置；降低 HTTP 重试；后台文章取消整条 HTTP 流水线重放；完整结果保存后可恢复。以上在当前源码存在，不能重复建议为尚未实施的方案；仍需验证线上部署版本。

正文与修复保留用户选择的型号，未统一关闭思考。既有 docs/api-cost-reduction-2026-09-07.md 记录一组历史样本中 Pro 输出 6235 Token、其中思考 4857 Token，耗时 119.3 秒。该记录说明思考成本值得测试，不代表本轮在线测量或所有文章都如此。

在相同资料、模板和题目上比较当前型号的默认思考与非思考／较低思考配置，统计最终可用率、总时间、修复率和每篇合格稿费用。通过后再决定文章专用默认策略，不改变其他模块或用户明确选择。

## 实施顺序与验收

**第一批：先解决用户直接报错。** 修完整响应生命周期；补阶段错误记录；统一预算实际行为和界面说明；正文一生成即保存。验收为响应体期间及时取消、任务恢复不重复正文、排队与上游错误可分辨、已有稿可找回。

**第二批：减少无效返工。** 统一冲突事实措辞；去重 Prompt 中重复资料；修正短问题误判；证据不足时使用一致的表达边界；纯格式问题本地修复；只针对真实内容问题调用模型。保留重要事实审核。

**第三批：做小样对照后降算力。** 选取覆盖正常与历史失败场景的 20–30 条同源题目，比较优化前后。实测有费用，应在实施时明确实验范围；本轮没有执行。再决定思考策略、正文专用型号、长度预算与批量证据复用。

每个任务至少关联 jobId／generationId、阶段、attempt、供应商请求 ID、模型、Prompt 版本、输入输出 Token、思考 Token、排队耗时、请求耗时、finish_reason、错误分类。当前 ai-usage 有模块 task 和用户、型号、账号等字段，但没有这些完整的单篇关联信息。

验收应同时看：①任务硬失败率；②首次成稿率；③最终可发布率；④修复触发率；⑤P50/P95 总耗时；⑥每篇最终合格稿总费用；⑦失败且 usage 未知的请求数量。用户积分退款与厂商费用分别统计。未取得账单前，不承诺固定降本百分比。
