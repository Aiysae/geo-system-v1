## 对原优化方案的修正

前两阶段改动通过本地验证，但尚未部署。本次证据表明，仅部署 Prompt 修正和草稿检查点仍不足以解决批量故障传播。

建议后续按以下顺序实施并分别验收：

1. **控制批量失败传播。** 区分暂时冷却／繁忙与欠费／无权限／未配置型号。暂时不可用时沿用现有持久任务队列延后处理，保留取消与总等待上限，不对剩余任务逐条立即报失败，也不额外重发已经完成的模型阶段。真实配置或账务故障给出明确批次提示。验收要覆盖连续超时、恢复后续跑、取消、超限退出、扣费与退款不重复。
2. **确认型号实际生效。** 对照后台默认值、账号允许型号和批次保存型号；在新任务创建前展示／校验实际型号。已有批次的型号变更应显式处理，不静默改历史任务。尚不直接把线上改成 Lite：目前没有其账号开通证据。
3. **再做思考模式小样对照。** 使用具备目标型号权限的账号和合成资料，对比默认／关闭思考的耗时、Token 与质量通过率。先少量通过再扩大，最终按每篇合格稿的完整路径计算费用；不能仅按正文长度估算。
4. **发布后的实际验收。** 核对硬失败率、暂缓任务的恢复率、修复率、P50/P95 和费用。把健康探测、短视频、长文、批量子任务分开统计。

结论：已有生产证据支持“调用超时 + 账号池可用性下降 + 批量任务快速失败传播”是当前重要原因，并有显著思考 Token 消耗。不能把问题简单归结为模型质量差，也不能认定切换 Lite 已在线上文章链路生效。
